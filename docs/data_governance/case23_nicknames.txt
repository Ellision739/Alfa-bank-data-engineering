DATA GOVERNANCE · КЕЙС №23
Классификация никнеймов игроков Dota 2

1. DATA LINEAGE · ПРОСЛЕЖИВАЕМОСТЬ ДАННЫХ

Основной поток

dota_data.players
  → lakehouse.raw.pg__players
  → lakehouse.stage.case23_nickname_clean1
  → lakehouse.stage.case23_nickname_unique1
  → lakehouse.mart.case23_nickname_1000_b01 и lakehouse.mart.case23_nickname_1000_single
  → аналитика в JupyterHub, запрос для датасета Superset через Trino.

Ветка H2

lakehouse.raw.pg__matches + lakehouse.raw.pg__match_players
  → связь по match_id, участник определяется по (match_id, player_slot)
  → связь с CLEAN по account_id и с разметкой по nickname_key
  → оценка разницы долей поражений в JupyterHub.

Прослеживаемость полей

• dota_data.players.personaname → RAW.personaname → CLEAN.original_nickname → CLEAN.normalized_nickname → UNIQUE.normalized_nickname.
• UNIQUE.nickname_key — SHA-256 от нормализованного ника в UTF-8. Ключ передаётся в MART и используется для соединения ответа с текстом и эталонной разметкой.
• tags, state, aggression, confidence и needs_review формирует LLM по тексту ника. Для воспроизводимости сохраняют SQL отбора, промпт, схему ответа, модель при наличии метаданных и идентификатор прогона.
• Для H2 ноутбук выводит ID снимков Iceberg CLEAN, MATCHES и MATCH_PLAYERS. Для исторических матчей используется последний доступный ник аккаунта. По этим данным нельзя установить, каким был ник в момент матча.

Подтверждено в Marquez звено от источника и RAW до CLEAN. Для пилота в Airflow видна входная зависимость от UNIQUE. Сквозное автоматическое отображение обеих MART и происхождения их колонок в Marquez требует отдельной проверки. Для демонстрации сохранить ссылку на граф и сверить имена датасетов с выводом Airflow и Trino.


2. DATA QUALITY · КОНТРОЛЬ КАЧЕСТВА ДАННЫХ

RAW и CLEAN

• Проверяем количество строк, пропуски и повторы account_id, диапазоны времени загрузки и изменения источника.
• CLEAN сохраняет исходный ник и нормализует пробелы и регистр. Каждый вход получает статус valid, missing или invalid. Причины исключения доступны в exclusion_reason: NULL, пустая строка после нормализации, управляющие символы, длина свыше 100 символов или отсутствие букв и цифр.
• Признаки has_cjk, has_cyrillic и has_latin помогают разбирать смешанное письмо. Валидные ники с CJK сохраняются. По одному CJK-флагу нельзя определить язык, а неполное покрытие Unicode учитывается как ограничение флага.

UNIQUE

• Включаем только valid. Одна строка на нормализованный ник. Проверяем уникальность текста и ключа, отсутствие пустых значений и совпадение ключа с SHA-256.
• Проверяем, что сумма source_occurrences совпадает с числом valid в CLEAN. Сверяем набор ников и число появлений каждого ника в двух таблицах.
• На проверенном снимке от 14.11.2026 в CLEAN было 1 752 932 строки, из них 463 633 валидные. В UNIQUE было 366 459 ников. SQL-аудит вернул OK. Дедупликация убрала 97 174 повторные строки перед отправкой на классификацию. Это потенциальная экономия обработки при одном ответе на уникальный ник.

MART и аналитика

• На вход LLM передаются nickname_key и normalized_nickname. На выходе проверяем наличие ключа, соответствие входу, уникальность и число ответов относительно фактического входа каждого прогона. Успешный статус Airflow сверяем с записанными строками и покрытием.
• Сверяем допустимые значения тегов и статусов, согласованность полей, диапазон confidence от 0 до 1 и формат needs_review. Статус unknown сохраняем для отчёта о покрытии. Флаг needs_review используется для отбора спорных примеров. Confidence хранится как оценка модели.
• Подтверждены 300 ответов в двух MART, 100 и 200. В одном из прогонов SQL вернул 1 000 входных строк, а в MART записалось 200. Полноту контролируем сравнением ключей до и после запуска. Причину ограничения проверяют по логам процесса.
• Для H1 полнота записи и корректный формат проверяются отдельно от качества тегов. Сравниваем правила и LLM по F1 на одинаковых ключах с отдельной разметкой. Встроенная разметка на 300 ключей черновая, 286 из них вошли в расчёт F1. Для итогового вывода нужна проверка меток командой.
• Для H2 проверяем покрытие соединений, число уникальных аккаунтов по группам и общие сочетания ранга, режима, лобби и стороны. Фактическая оценка H2 требует запуска на таблицах матчей. Ноутбук показывает, на каком шаге теряются строки.


3. КАТАЛОГИЗАЦИЯ И АРХИТЕКТУРА СЛОЁВ · RAW → STAGE → MART

RAW · lakehouse.raw.pg__players
Назначение — хранение исходных записей загрузки игроков. Сохраняются account_id, personaname и поля технического аудита job_id, sys_insert_stamp, src_modified_stamp.

STAGE CLEAN · lakehouse.stage.case23_nickname_clean1
Назначение — очистка с сохранением связи с исходной записью. Гранулярность — одна строка на входную запись RAW. Сохраняются поля технического аудита RAW, исходный и нормализованный ник, признаки, статус, причина исключения и stage_loaded_at.

STAGE UNIQUE · lakehouse.stage.case23_nickname_unique1
Назначение — подготовка входа для классификации. Гранулярность — одна строка на валидный нормализованный ник. Ключ — nickname_key. Хранятся признаки, source_occurrences, число исходных вариантов и unique_loaded_at. Связь с источником восстанавливается через CLEAN.

MART · lakehouse.mart.case23_nickname_1000_b01 и lakehouse.mart.case23_nickname_1000_single
Назначение — хранение результатов LLM. Гранулярность — одна строка на nickname_key внутри прогона. Для объединения прогонов сверяются ключи и происхождение результата. В выводах для экспертов и в Superset показываются агрегаты по статусам, тегам и письменности. Сырые тексты ников и account_id нужны только для рабочей проверки.

В паспорте каждого объекта фиксируются владелец, назначение, источники, ключ, расписание, права доступа, глубина хранения и допустимая задержка. Именованных владельцев, срок хранения и числовой SLA нужно согласовать с командой платформы.


4. SLA И СОБЫТИЙНАЯ СИНХРОНИЗАЦИЯ · AIRFLOW

• Последовательность обновления — RAW → CLEAN → UNIQUE → MART. MART нужен успешный выход UNIQUE. CLEAN является зависимостью UNIQUE и участвует в цепочке через него. Для H2 дополнительно требуются RAW-таблицы матчей и участников.
• В Airflow для CLEAN показана зависимость от lakehouse://raw/pg__players, для пилотной MART — от lakehouse://stage/case23_nickname_unique1. Автоматический триггер и его фактическое срабатывание для обеих MART с результатами на 300 ников нужно подтвердить по настройкам DAG и истории запусков.
• Почасовой цикл — ориентир для проверки свежести. Числовой SLA подтверждается по журналу: время успешной загрузки RAW и STAGE, событие входного датасета, длительность run_transform, число сохранённых строк и время успешной публикации MART. Для пакетных LLM-прогонов отдельно фиксируются охват и статус каждой партии.
• Регламент при сбое. Найти этап, на котором упал прогон, по логам Airflow. После устранения причины повторить запуск, сверить входные ключи и выход и проверить последний успешный набор перед обновлением отчёта. Для повторного запуска по возможности зафиксировать исходный снимок, выборку, параметры запроса и схему ответа. Семантика дозаписи и продолжения с места сбоя для LLM-прогонов требует подтверждения.
