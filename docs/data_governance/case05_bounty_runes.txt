DATA GOVERNANCE — КЕЙС №5 «BOUNTY RUNES»

Владелец данных — команда кейса №5. За Airflow, сверку слоёв и актуальность витрины отвечает назначенный участник команды, за определения метрик и сверку с ноутбуком — аналитик кейса. Витрина используется в Superset для проверки гипотез о золоте в первые 10 минут и о первой башне.

1. DATA LINEAGE — ПРОСЛЕЖИВАЕМОСТЬ ДАННЫХ

Путь данных проходит от PostgreSQL и MongoDB через таблицы lakehouse.raw к двум STAGE, затем к lakehouse.mart.bounty_05_outcomes. Superset читает витрину через Trino.

• RAW pg__matches, pg__match_players, mongo__rune_events и mongo__tower_death_events → STAGE bounty_05_match_events. Из duration отбираем матчи нужной длины. Из rune, action и time считаем подборы, сторону определяем по match_id, аккаунту и is_radiant. Из time, radiant и dire восстанавливаем сторону, взявшую первую башню.
• STAGE bounty_05_match_events и RAW pg__match_players, mongo__gold_events → STAGE bounty_05_match_gold. Суммируем знаковые amount за первые 10 минут по сторонам. Поле reason позволяет отдельно посчитать положительные начисления без BOUNTY.
• Оба STAGE → MART bounty_05_outcomes по match_id. Поле gold_ahead показывает, опередил ли лидер по рунам соперника по зафиксированному золоту. Поле rune_leader_took_first_tower показывает, совпал ли лидер по рунам к 12:00 со стороной, взявшей первую башню за весь матч.

Marquez получает события OpenLineage о задачах, их входах и выходах. На присланном скриншоте подтверждена ветка до bounty_05_match_events. Полный граф Marquez до MART и автоматические связи на уровне колонок по имеющимся материалам ещё не подтверждены. Происхождение показателей на уровне полей зафиксировано в SQL и в bounty_lineage/README.md. Графики Superset на витрине уже получены.

2. DATA QUALITY — КОНТРОЛЬ КАЧЕСТВА

• Ключи. Матч идентифицируем по match_id, строку состава — по (match_id, player_slot), события — по (match_id, id). В проверенных срезах пяти RAW-таблиц по этим ключам не обнаружено пустых или невалидных ключей, повторов и конфликтов. Для STAGE и MART проверяем равенство COUNT(*) и COUNT(DISTINCT match_id), а также равенство числа строк первого STAGE и MART.
• Сопоставление команды. Ищем игрока по (match_id, steam_account_id) события и (match_id, account_id) состава. Используем соответствие только с однозначными слотом и стороной. Неизвестная сторона руны остаётся в знаменателе. Порог 70% считается достигнутым, если известных подборов команды уже достаточно независимо от стороны остальных рун.
• Золото. Окно [0, 600) секунд. Исключаем из золотой выборки матчи без подходящих событий, с пропущенным amount, с событиями без определённой команды или без положительных начислений у одной из сторон. При расчёте без BOUNTY также исключаем матчи с неизвестной причиной положительного начисления.
• Первая башня. Лидера определяем по наблюдаемым подборам в окне [0, 720) секунд. В расчёт входят матчи от 12 минут с однозначным лидером и однозначно определённой стороной первой башни за весь матч. Если первой упала башня Radiant, её взяла Dire, и наоборот.

В финальном прогоне Jupyter из 63 798 матчей, прошедших порог по рунам, в золотую выборку вошло 61 163. Исключено 2 635 матчей — в 2 547 события золота не удалось полностью привязать к командам, в 87 отсутствовали подходящие события и в 1 у одной стороны не было положительных начислений. Эти числа относятся к указанному прогону.

3. КАТАЛОГИЗАЦИЯ И АРХИТЕКТУРА СЛОЁВ

• RAW — исходные матчи, составы и события. Технические поля загрузки job_id, sys_insert_stamp и src_modified_stamp позволяют сопоставлять записи с загрузкой и проверять свежесть источников там, где эти поля доступны.
• STAGE — подготовка данных на уровне одного матча. bounty_05_match_events хранит счётчики рун, сторону первой башни и статусы, bounty_05_match_gold — суммы золота, разницы и статус качества для отобранных матчей.
• MART — bounty_05_outcomes, одна строка на match_id. Витрина содержит показатели обеих гипотез и статусы качества, по которым строятся выборки в Superset. В коде STAGE и MART технические поля RAW в результат не выводятся. Для аудита их запусков используем сведения Airflow, а для прослеживаемости — граф Marquez и SQL.

4. SLA И СОБЫТИЙНАЯ СИНХРОНИЗАЦИЯ

Порядок расчёта. Первый STAGE готовит события матча. Второй STAGE использует его для отбора золотой выборки. MART читает оба STAGE. Для согласованного обновления сначала подтверждаем успешное завершение обоих STAGE с учётом этого порядка, затем обновляем MART.

На скриншоте первого DAG в Airflow подтверждено расписание типа Dataset. Условие автоматического запуска MART после обновления обоих STAGE нужно сверить в настройках его DAG. Текущие SQL-запросы пересчитывают результат по доступной истории. Почасовое обновление, фактическая задержка и выполнение SLA по материалам кейса пока не подтверждены.

Для паспорта SLA фиксируем расписание, допустимую задержку, ответственного и время последнего успешного обновления каждого слоя. При приёмке сверяем статусы и журналы трёх DAG в Airflow, наличие таблиц и уникальность match_id в Trino. Отдельно проверяем, что в MART нет строк со статусом missing_gold_stage_row. Он означает, что матч должен был получить строку из золотого STAGE, но при соединении её не нашли.
